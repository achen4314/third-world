### 1.1 修订（20:50，实测后改了方案）

20:44 的一轮端口探测推翻了本节下方原方案的一个关键前提，记在这里，下文相应段落已同步修改：

| 原假设 | 实测 | 后果 |
|---|---|---|
| 80 端口由**主机 nginx** 持有，加 `/etc/nginx/conf.d/*.conf` 即可按 Host 分流 | 80 返回 `Server: nginx/1.31.4` + `X-Powered-By: Next.js` + `/auth/refresh` 跳转，Ubuntu 24.04 自带 nginx 是 1.24 → **这是 Docker 里的 Dify nginx** | 主机上没有 nginx 在听 80，加 conf.d **完全不生效**，还可能和 Dify 抢端口 |
| 用 `certbot --nginx` 签证书 | 主机可能没有 nginx 可挂钩；80 被占，HTTP-01 验证拿不到 | 改用 **Caddy 独占 443**，80 被占时它自动切 TLS-ALPN-01 验证，完全不碰 80 |
| 用子域名 `app.trthirdworld.online` | 主域名当前 **0 条记录**，子域只会再叠一层等待 | 直接上主域 `trthirdworld.online`，少一跳 |
| 443 只要服务起来就能访问 | `nc -z 47.95.117.212 443` → **closed**，22/80 才 OPEN | **云防火墙没放行 443**，这是一条独立的 P0 |

因此部署形态定为：**Dify 继续占 80，我们独占 443**（`deploy/Caddyfile`）；
TLS 未就绪前可用 **:8080** 过渡（`deploy/Caddyfile.http`），按 IP 也能验收。

## 3. 域名解析核查证据

截图（阿里云云解析 DNS · `trthirdworld.online` 免费版）显示「NS 地址不一致」黄条，分配值为 `dns11.hichina.com` / `dns12.hichina.com`，记录列表「没有数据」。

本机实测：

```
dig +short NS trthirdworld.online  → dns11.hichina.com. / dns12.hichina.com.
dig +short A  trthirdworld.online  → （空）
dig +short A  www.trthirdworld.online → （空）
```

**判定**：
- 注册商处的 NS **已经**指向阿里云分配的两台（与控制台一致），黄条多半是控制台查询缓存 / 生效延迟，可点「重新查询」复核；这不是当前的主要阻塞。
- 真正的阻塞是 **A 记录 0 条**：域名现在解析不到任何 IP，浏览器打不开。
- 建议添加（部署后按实际域名）：

| 主机记录 | 类型 | 记录值 | 用途 |
|---|---|---|---|
| `app` | A | `47.95.117.212` | 前端 + 后台控制台入口（推荐，隔离 Dify） |
| `@` | A | `47.95.117.212` | 可选，主域也指向本应用 |
| `www` | CNAME | `app.trthirdworld.online` | 可选 |

**不要**把现有 Dify 正在用的域名记录改掉。

## 4. 比技术更靠前的合规阻塞

服务器在**华北 2（北京）**，属于中国大陆境内节点。要在中国大陆通过域名对外提供 Web 服务：

1. **ICP 备案**：域名 `trthirdworld.online` 需在腾讯云备案系统提交，主体 + 网站信息，管局审核通常约 20 个工作日。未备案时，云厂商会对 80/443 的域名访问做拦截。
2. **公安联网备案**：上线后 30 日内在 `beian.gov.cn` 办理。
3. 若按 App 发布，还需 **App 备案**（工信部），且图标下名称、设置页、备案号、商店信息四处一致。
4. 本项目涉及 HRV / 睡眠等健康数据，境外 Supabase（us-east-1）与境内服务器并存会构成数据出境，累计 1 万人即触发标准合同/认证要求（见 `docs/06`）。

这几项都需要主体资质与实名，我无法代做，也不该在未备案时宣称「已公网可用」。

## 5. 已开发完成的后台管理控制台（`deploy/`）

| 文件 | 作用 |
|---|---|
| `deploy/admin-console.mjs` | 零依赖 Node HTTP 服务，默认 `127.0.0.1:8787` |
| `deploy/admin/index.html` | 管理界面：口令登录、连接配置、状态巡检、维护动作、日志 |
| `deploy/nginx.arc-training.conf` | ⚠️ **已弃用**（本机 80 属 Docker Dify，主机 conf.d 不生效），仅留给「主机 nginx 听 80」的其它机器 |
| `deploy/Caddyfile` | **当前方案**：独占 443，证书自动申请/续期，服务 `dist/`（三端 + 分发页）并按 path 分流管理控制台，不碰 80 |
| `deploy/Caddyfile.http` | 过渡方案：`:8080` 纯 HTTP，备案/证书未就绪时按 IP 验收 |
| `deploy/server-preflight.sh` | 上机先跑的只读巡查：端口归属、Docker 容器、主机 web 服务、防火墙、出网能力、既有站点目录 |
| `deploy/arc-admin.service` | systemd 单元，最小权限（`NoNewPrivileges` / `ProtectSystem` / `ProtectHome`；因需 reload 门面故以 root 运行，仅绑回环） |
| `deploy/install.sh` | 幂等安装脚本，含本机自检与 DNS 检查 |

**能力**
- 配置管理：写 `SUPABASE_URL` / publishable key / 域名 / 是否允许运行时覆盖 → 生成 `prototype/env.js` **并自动重建 `dist/`**（三端各自的 env.js 才会更新；这是「把数据库连接配到服务器上的应用」的完整链路）。
- 状态巡检：主机负载与内存、磁盘、门面配置校验（caddy/nginx 双兼容）、服务状态、**本机 443 端到端探活**、域名 A 记录、Supabase Auth 连通性。
- 日常维护：健康检查、门面配置校验、重载门面、端口占用、证书状态、重启管理服务、查看日志。
- **安全边界**：只绑回环地址，公网入口由 Caddy 反代；不额外开端口。
- 不设 `ARC_ADMIN_TOKEN` 直接拒绝启动；所有 `/api/*` 要 Bearer token。
- 维护动作是**固定命令白名单**，不接受客户端传来的命令字符串（已测：`{"name":"rm -rf /"}` 被拒）。
- 只接受 `sb_publishable_` 开头的 key（已测：`sb_secret_` 被拒）；GET 配置时 key 掩码回显；配置文件 0600。
- 不碰 Dify 配置、不碰数据库密码、不覆盖业务数据。

**本地冒烟测试**（`ARC_ADMIN_ROOT` 指向临时目录，未改动仓库里的 `env.js`）：
`401 未授权 → 带 token 读配置 → 状态巡检 7 项 → 保存配置并生成 env.js → 拒绝 secret key → 拒绝白名单外动作`，全部符合预期。

#     → 143 项自检：控制台 200 / 无口令 /api/config 401 / 静态站 200 / env.js 200
#     → Caddy 未装则 apt 装；443 被占则拒绝执行（不抢端口）

#    验证：curl -I https://trthirdworld.online/  →  200；控制台「证书状态」可看签发记录
