# 计算与指标专项审查

> 2026-11-16 00:20 · 基于真实库实测 + 逐行读口径实现，不是复述旧清单
> 核验：`node tools/verify-data.mjs` → 22 项：✓ 17 / ! 2 / ✗ 2（修掉一处工具误报后）

## 结论先说

**有一个每天都会遇到的 P0**：今天（11-16）打开应用，ACWR、CTL、ATL、TSB、就绪度**全是 null**。
不是数据没同步，是「休息日状态量只在重算时推进，而只有写入训练才会触发重算」。
浏览器实机已复现：今日页显示「负荷 · ACWR(EWMA) —」。

另外有一个结构性的算法错误：**ACWR(rolling)、TM、TS 三项永远算不出来**，
库内 15 个已产出指标里根本没有它们；界面写的「窗口有效天数不足」不是数据问题，是门槛写错。

## P0-1 休息日状态量没有推进到「今天」

**实测证据**

```
daily_metrics 最后日期     2026-11-15（北京时）
arc_local_today()          2026-11-16
arc_daily_summary(今天)    acwr=null atl=null ctl=null 就绪=null
```

`arc_daily_summary` 是纯读：
```sql
select ... into v_load from public.daily_metrics
where athlete_id = p_athlete and metric_date = v_day ...
```
今天没有行，就整块返回 null。它**不会**用最后一次状态量按衰减推算到今天。

`arc_recompute_metrics` 里 0012 确实写了休息日衰减，但唯一的调用入口是
`arc_after_activity` 触发器（0010 改为 `perform arc_recompute_metrics(v_athlete, null)`）——
**只有写入/修改 activities 才触发**。今天没练，就没有重算，指标表就停在最后训练日。

`verify-data` 的两项失败正是这个：
```
✗ 负荷/EWMA 与独立重算一致   16 天 · 该有为空 2
✗ 重算幂等                  140 行 · 变化 0 · 消失 0 · 新增 4
```
「新增 4」= 在事务内跑一次重算会补出 4 行，说明**当前库里的状态量是不完整的**。

**影响**：每天首次打开（写当天训练之前）今日页、就绪度、周期建议全部显示「—」；
连续休息越久，缺口越大。这是上线后最容易被用户感知的问题。

**修法（不改历史数据）**：在 `arc_daily_summary` 里加只读 fallback——
取 `metric_date < v_day` 的最后一组 ctl/atl/acu/chr，按 0012 的同一组系数
（ctl−ctl/42、atl−atl/7、acu−0.25·acu、chr−0.069·chr）逐日推进到 `v_day`，
只用于本次返回，不写库、不改历史曲线。或加每日定时重算（需要 pg_cron / 外部调度）。
前者更安全，也符合「服务端唯一计算源」。

## P0-2 ACWR(rolling) / TM / TS 结构性永不产出，且分子分母口径不一致

`20261114000012_rest_day_decay.sql`：
```sql
v_roll := case when v_w7n = 7 and v_w28n >= 26 and v_w28sum > 0
               then (v_w7sum / 7.0) / (v_w28sum / v_w28n) else null end;
v_tm   := case when v_w7n = 7 and v_w7sd > 0 then (v_w7sum / 7.0) / v_w7sd else null;
```
`v_w7n` 数的是**有训练记录的天数**，却要求 `= 7`（一周七天全练）。
真实库实测任意 7 日窗口的最大训练天数是 **6**：
```
n7: 6, 6, 6, 6, 6, 5 ...
```
只要有任何休息日，条件就永远不成立。库内 15 个已产出 metric_id 里
**没有 `acwr.rolling` / `tm` / `ts`**，与代码一致。SQL 注释写「只看有记录的日历天」，
与 `= 7` 的硬门槛自相矛盾。

**第二层错误**：分子 `/7.0` 按日历天，分母 `/v_w28n` 按训练天数——
急性窗被摊薄、慢性窗被抬高，ACWR 会系统性偏低。标准 rolling 口径
应为「7 日总负荷 / 28 日总负荷 × 4」，或两侧都按日历天取均值、休息日按 0 计。

**第三层**：前端 `computeLoad()` 又是第三套：
```js
const rolling = (i >= 27 && w7.valid === 7 && w28.valid >= 26) ? w7.mean / w28.mean : null;
```
`stats().mean` 是**有效值均值**（除以有效天数），所以前端是 mean/mean，
服务端是 `/7` 与 `/n` 混合。同一个「ACWR (rolling)」标签下有三套口径。

**影响**：ACWR 双口径实际只剩 EWMA 一个可用；TM/TS（单调性/应变）完全没数据。
界面把它们显示为「不可计算 · 窗口有效天数不足」，把算法 bug 伪装成数据不足。

**修法需要你先定口径**（见文末）。

## P0-3 重算不清理「已不再成立」的旧值

`arc_recompute_metrics` 休息日只删两类日聚合量：
```sql
delete from daily_metrics ... and metric_id in ('tl.srpe','load.week');
```
状态量走 `insert ... where m.val is not null on conflict do update`，
**当某指标当天算出 null 时，既不插入也不删除**。
所以只要某天曾经算出 `acwr.rolling` / `tm` / `ts` / `tsb`，
之后数据变了、或变成休息日、或条件不再满足，**旧值会永久残留**。

`tsb` 首日为 null 也走同一路径。目前库里恰好没有 rolling/tm/ts 行，
所以还没暴露；但 P0-2 一旦修好（开始产出这三项），这个清理缺口立刻会产生脏数据。

**修法**：在写入前，把本函数负责的 9 个 metric_id 在该日**先整体删掉再写**，
或对每个算成 null 的指标显式 `delete`。属于幂等性修复，不改口径、不动历史值以外的数据。

## P1-1 首日 CTL / ATL 被初始化成当天 TL

实测第一行：
```
2026-10-31  tl=476  ctl=476  atl=476  acwr=1.0000
```
代码：
```sql
v_ctl := case when v_ctl is null then v_tl else v_ctl + (v_tl - v_ctl)/42 end;
v_atl := case when v_atl is null then v_tl else v_atl + (v_tl - v_atl)/7 end;
```
标准 EWMA 应从 0 起步（首日 CTL ≈ 476/42 ≈ 11.3、ATL ≈ 68）。
现在首日直接把两个状态量拉到 476，**虚高 42 倍 / 7 倍**，
ACWR 恰好等于 1.0000（纯属构造假象），TSB=0。前 42 天的整条曲线都被抬高。

**影响**：新账号/新运动员开局几周的所有负荷结论都不可信，且看不出来为什么。

## P1-2 前端 `computeLoad()` 与服务端仍不一致

`prototype/app.js:89`：

| 项 | 前端 | 服务端 0012 |
|---|---|---|
| 休息日 CTL/ATL/ACU/CHR | **完全不变（延续）** | 按 0 负荷衰减 |
| EWMA(ACWR) 门槛 | `w7.valid >= 5` | 只要求 `chr > 0` |
| rolling | `w7.mean / w28.mean` | `(w7sum/7) / (w28sum/n)` |
| TM / TS | `w7.valid === 7` | `v_w7n = 7` |

文件注释自己写着「两套实现迟早会算出两个数」。
真库模式走 `A.SRV`（服务端值）所以暂未暴露，但未登录/演示路径、
`chartLoadTrend` 等仍会用旧算法，且日后任何一处改动都会让两边分叉。

## P1-3 休息日的 `source` 沿用上一个训练日

`v_src` 只在 `if v_cnt > 0` 分支里被 `select ... into v_src` 赋值，
休息日分支不重置，随后所有状态量都写 `coalesce(v_src, 'manual')`。
也就是休息日（当天没有任何原始数据）的 CTL/ATL/ACWR 会被标成上一个训练日的
`device` / `import` / `api`。当前库恰好全是 `manual` 源所以没暴露，
一旦接入设备就会变成**溯源错误**。

---

## P1-4 全量重算 O(n²)，且每次写训练都触发

`for d in generate_series(v_start, v_to, ...)` 每天做 3 次 activities 扫描
（当日 / 7 日 / 28 日），`v_to` 默认算到今天。触发器在每条 activities 的
INSERT/UPDATE/DELETE 后都调一次全量重算。记录积累到一年就是
365 × 3 次查询 / 每次写一条训练。批量导入时会退化得很明显。
