# 域名绑定：不依赖服务器、不依赖备案的即时方案

> 2026-11-15 13:30 实测整理
> 适用前提：用户明确「绑域名不是服务器」，且 `trthirdworld.online` 备案中 / 未备案。

## 1. 为什么原来那条路走不通

| 环节 | 状态 | 说明 |
|---|---|---|
| DNS 解析 | ✅ 已完成 | `@` / `www` → `47.95.117.212`，在 223.5.5.5 与 8.8.8.8 均生效 |
| 服务器上有我们的服务 | ⛔ 没有 | `47.95.117.212:80` 是 Dify 的 nginx；443/8080/8443 均 closed；SSH 公钥未被授权 |
| 备案 | ⛔ 未完成 | 域名请求在**阿里云机房入口**就被 403 拦截，根本没到服务器 |
| 结论 | — | **DNS 指向 ≠ 域名可用**。指向一个地址，不代表那个地址上有应用 |

备案拦截的实测证据（同一个 IP、同一个 80 端口，只换 Host 头）：

```
curl http://47.95.117.212/                       → 307  nginx/1.31.4   （Dify，正常）
curl -H 'Host: trthirdworld.online' 同一地址     → 403  Server: Beaver
                                                   <title>Non-compliance ICP Filing</title>
```

连带影响：Caddy 申请 Let's Encrypt 证书时，HTTP-01 走 80 会被这个 403 挡，
TLS-ALPN-01 走 443 也过不了机房校验 → **证书签不下来**。
即「部署成功」会表现为「服务在跑、域名 403」，容易被误判成部署失败。

## 2. 已经完成的准备（无需用户操作）

把三端独立版本推送到仓库的 **`gh-pages` 分支**，并写入 `CNAME`：

```
gh-pages/
├── CNAME                      → trthirdworld.online
├── .nojekyll
├── index.html                 → 设备识别分发页
├── version.json               → 三端核心一致性校验
├── iphone/  ipad/  mac/       → 各自 manifest / sw / 图标 / env.js
```

远端已确认存在 `gh-pages` 分支；产物经 CDN 逐一校验：
`index.html` 200、`CNAME` 200（内容 `trthirdworld.online`）、`version.json` 200、
三端 `manifest.webmanifest` / `sw.js` / `env.js` 均 200。

**GitHub Pages 已自动启用并识别了自定义域名**，铁证：

```
curl -I https://achen4314.github.io/third-world/
→ HTTP/2 301   server: GitHub.com
→ location: http://trthirdworld.online/
```

这个 301 只会在 Pages 已启用且 `CNAME` 生效时出现。
目前跟随跳转得到 403，是因为 DNS 还指向阿里云那台未备案的机器——**只差改 DNS 这一步**。

## 3. 用户需要做的：改 DNS（阿里云云解析 DNS）

打开 云解析 DNS → `trthirdworld.online` → 解析设置。

### 3.1 删除 / 修改现有记录

| 操作 | 主机记录 | 类型 | 原值 | 新值 |
|---|---|---|---|---|
| 修改 | `@` | **A** | `47.95.117.212` | 见下方 4 条 A 记录 |
| 修改 | `www` | **CNAME** | `47.95.117.212`（或 A） | `achen4314.github.io` |

根域 `@` 建议用 A 记录（GitHub 官方推荐，比 CNAME 更稳），**同时添加 4 条**：

```
@   A   185.199.108.153    TTL 600
@   A   185.199.109.153    TTL 600
@   A   185.199.110.153    TTL 600
@   A   185.199.111.153    TTL 600
```

> 这 4 个是 GitHub Pages 官方 Anycast IP。多条 A 记录是轮询冗余，不是填错。
> **建议把 TTL 改为 600**：实测用户首次配置时阿里云返回的是 TTL 3600，
> 导致旧记录在本地路由器 / 运营商缓存里最长要 1 小时才过期。
> 将来切回自己服务器时，短 TTL 能让切换在 10 分钟内完成。

`www` 用一条 CNAME：

```
www   CNAME   achen4314.github.io    TTL 600
```

> 若阿里云不允许 `@` 同时存在 4 条 A，至少填 `185.199.108.153` 一条即可先通。

### 3.2 保存后等待

- DNS 生效：通常 1–10 分钟（TTL 600）。
- HTTPS 证书：GitHub 检测到 DNS 正确后自动签发 Let's Encrypt 证书，通常 15 分钟–1 小时。
  期间用 `http://` 可能先通、`https://` 报证书错误，属正常。
- 建议在仓库 Settings → Pages 勾选 **Enforce HTTPS**（自定义域名生效后方可勾选）。

## 5. 影响面与回滚

**不受影响**：
- `http://47.95.117.212/` 仍是 Dify（按 IP 访问，与域名解析无关）。
- 服务器上的任何文件、容器、端口、数据库、密码都没被改动。
- 备案流程照常进行，不受 DNS 目标变更影响。

**变更的只有一件事**：`trthirdworld.online` 这个名字指向哪个 IP。

**回滚**：把 `@` 的 4 条 A 记录改回 `47.95.117.212`、`www` 改回原值即可，
TTL 600 下几分钟内生效；`gh-pages` 分支可保留不删，不影响 `main`。

**备案通过后想切回自己的服务器**（两步）：
1. DNS：`@` / `www` A 记录 → `47.95.117.212`；
2. 服务器：解决 SSH 通道与 443 放行后执行
   `ARC_ADMIN_TOKEN='…' bash deploy/bootstrap.sh https`（见 `docs/14` 的隔离契约）。
   两条链路互不依赖，可随时切换。

结论：**服务端与 DNS 侧已 100% 就绪**，剩下两项都是「等待」而非故障：

1. **本地 DNS 缓存**：权威记录实测 TTL 为 **3600**（不是建议的 600），旧值在路由器 /
   运营商递归里最长需 1 小时过期。清本机缓存需管理员密码（`sudo killall -HUP mDNSResponder`），
   本次环境无 sudo 权限，未执行。
   **立刻可验证的办法**：用手机关掉 WiFi、走蜂窝网络打开 `http://trthirdworld.online/`，
   运营商 DNS 用的是新记录，应直接打开应用。
2. **自定义域名证书**：GitHub 在检测到 DNS 正确后自动向 Let's Encrypt 申请，
   通常 15 分钟–1 小时，最长 24 小时。期间 `http://` 可正常访问（未开 Enforce HTTPS），
   `https://` 会报证书名称不匹配。**证书签好后**在仓库 Settings → Pages 勾选
   `Enforce HTTPS`；若超过 1 小时仍未签发，把 Custom domain 删掉再填一次可触发重新检查。

## 6. 这条路的取舍（如实说明）

| | 说明 |
|---|---|
| 优点 | 不需要 SSH、不需要 443、不需要等备案、不碰 Dify；域名**现在就能用**；HTTPS 由 GitHub 自动签发 |
| 代价 | 静态托管在境外，国内访问速度可能不如大陆机房；GitHub Pages 不适合承载需要服务端写操作的场景 |
| 数据安全 | 三端应用本来就是纯浏览器端直连 Supabase（RLS 行级权限），静态托管不降低安全性；`env.js` 里只有设计上公开的 publishable key |
| 后台控制台 | `deploy/admin-console.mjs` 属于服务端程序，**不在这条静态链路上**。需要它时仍要部署到自己的服务器（备案后） |
| 合规 | 境外 IP 不触发大陆机房的备案网关。若后续主体备案完成并切回大陆 IP，按常规流程接入即可 |
