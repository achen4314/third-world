# 隔离契约：本次部署与「另一个挂载点」互不干扰

时间：2026-11-14 21:10
对象：服务器 `47.95.117.212`（轻量应用服务器 `Ubuntu-gaxl`，Ubuntu 24.04，2C4G）
另一个挂载点：**80 端口上的 Dify**（Docker 中的 nginx 1.31.4 + Next.js，带登录）

---

## 1. 一句话承诺

**我只在一个新目录 `/opt/arc-training` 里写文件、只在一个没人用的端口 443 上听、
只用自己的 systemd 单元和自己的低权限用户。Dify 的文件一个字节都不写、不动它的容器、
不碰它的 nginx 配置、不占它的 80。**

这不是口头保证——本文第 4 节是**可执行的取证方法**，第 5 节是**精确回滚**。

---

## 2. 写入面白名单（只碰这些）

| 类型 | 路径 / 对象 | 说明 |
|---|---|---|
| 目录 | `/opt/arc-training/` | 项目本体，全新建；不存在则创建 |
| 配置 | `/etc/arc-training/admin.env` | 后台口令，0600 root |
| 单元 | `/etc/systemd/system/arc-admin.service` | 新建，名字唯一 |
| sudoers | `/etc/sudoers.d/arc-admin` | 只放行**一条**命令：`systemctl reload-or-restart caddy` |
| 门面 | `/etc/caddy/Caddyfile` | 仅在**文件不存在**或**含 `ARC-MANAGED` 标记**时写入；否则先备份 `.bak.<时间戳>` |
| 日志 | `/var/log/caddy/` | 仅 `arc-access.log` |
| 取证 | `/var/lib/arc-guard/` | before/after 快照 |
| 用户 | `arcadmin`（系统用户，nologin） | 控制台专用 |
| 端口 | **443**（Caddy）、**127.0.0.1:8787**（控制台，仅回环） | 443 实测空闲 |

## 3. 绝不触碰清单（碰了就是事故）

| 对象 | 为什么危险 | 技术上的保护 |
|---|---|---|
| **80 端口** | Dify 的门面 | 我们**从不 bind 80**；Caddy 配置里没有任何 `:80` server 块；证书验证走 TLS-ALPN-01（走 443），不需要 80 |
| **主机 nginx** | 一旦装了就抢 80 → Dify 立刻挂 | 安装脚本**不安装 nginx**；`nginx.arc-training.conf` 已弃用 |
| `/etc/nginx/**` | Dify 若从宿主读配置 | 不读不写不 reload |
| **Docker** | 容器 = Dify 本体 | 全程不执行任何 `docker` 写命令（`guard-dify.sh` 里仅 `docker ps/images` 只读查询） |
| `/var/lib/docker` | 容器数据 | systemd 里 `InaccessiblePaths=/var/lib/docker`，控制台进程根本看不见它 |
| `/opt/dify` | 若存在即别人的站点 | 同样 `InaccessiblePaths` |
| 数据库密码 | 你的硬约束 | 全程不碰。Supabase 只从浏览器直连，服务器上不存任何数据库凭据 |

## 4. 三道验证（每道都有可看的结果）

### 第一道：部署前后快照比对（自动，install.sh 内置）

`deploy/guard-dify.sh` 只读采集这些「一旦变化就说明被我们动了」的事实：

- 80 / 443 / 8080 / 8787 的**监听者 PID+进程名**
- `docker ps -a` 全部容器（ID/名字/镜像/状态）与镜像列表
- **80 端口的 HTTP 响应码 + `<title>` + `Server` 头**
- `/opt`、`/opt/dify`、`/root`、`/var/www`、`/etc/nginx`、`/var/lib/docker` 的 mtime

部署前 `snapshot before`，部署后 `snapshot after`，然后 `diff`：

```
════ 与 Dify 相关的关键项比对 ════
  ✓ 全部一致：端口归属、容器集合、80 端口响应、Dify 目录 mtime 均未变化
    → 结论：本次操作没有触碰另一个挂载点
```

**只要有任意一行不同，脚本会把差异原文打出来**，我们逐条查清才能继续。

### 第二道：80 端口内容必须「还是 Dify」

任何时候执行：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://47.95.117.212/     # 应仍是 307
curl -s http://47.95.117.212/ | grep -o '<title>[^<]*</title>'      # 应仍是 <title>Dify</title>
```

这是最直观的证据：域名走 443 是我们的站，IP:80 走 Dify 的站，两者并存。

### 第三道：回滚演练（`deploy/uninstall.sh`）

回滚只删白名单内的路径，且带**双重断言**：
- 路径必须以 `/opt/arc-training`、`/etc/systemd/system/arc-admin.service` 等白名单前缀开头；
- 命中 `/opt/dify`、`/var/lib/docker`、`/etc/nginx`、`/opt`、`/etc`、`/root` 等受保护路径 → **直接报错退出**；
- `Caddyfile` 无 `ARC-MANAGED` 标记 → 保留不动；
- 不 stop/restart 任何既有服务。

默认**干跑**（只打印将删什么），确认后才 `--yes` 真删。

## 5. 运行期隔离（不是只靠「小心」）

| 手段 | 具体做法 | 隔离了什么 |
|---|---|---|
| 专用用户 | 控制台以 `arcadmin`（system、nologin）运行 | 被攻破也读不到 root/docker 的文件 |
| systemd 沙箱 | `ProtectSystem=full`、`ProtectHome=true`、`PrivateTmp=true`、`NoNewPrivileges=true` | `/usr`、`/etc`、`/boot` 只读；看不到家目录 |
| 路径屏蔽 | `InaccessiblePaths=/var/lib/docker /opt/dify` | 进程层面看不见另一个挂载点 |
| 写权限收敛 | `ReadWritePaths=` 只有 `prototype/` 与 `deploy/runtime/` | 全盘只有这两个目录可写 |
| 特权单点 | sudoers 只放行 `systemctl reload-or-restart caddy` | 不能停别人的服务、不能改别人的单元 |
| 端口隔离 | Caddy 只配 443；控制台只绑 `127.0.0.1` | 不抢 80，也不额外暴露端口 |
| 失败即停 | 443 被占 → 拒绝执行；sudoers 校验失败 → 自动删掉该文件；Caddyfile 非我们写的 → 先备份 | 不会「硬着头皮装」把别人撞挂 |

---

## 6. 唯一真正共享的资源：内存

进程、端口、文件、配置全部隔离，但**内存和 CPU 是共用的**。实测 Dify 已用 2.67/4.0 GiB，
我们这套（Node 控制台 + Caddy）稳态约 60–90 MB。安装脚本会检查 `MemAvailable`，
低于 300 MB 时告警。长期若内存吃紧，优先给 Caddy 加 `memory` 限制，而不是动 Dify。

另外有一个**未来可能**的冲突点，现在不存在：如果哪天 Dify 自己也要上 HTTPS 占用 443，
就和我们的门面撞了。到时要么它继续用 80 反代，要么我们把门面挪到别的端口。它当前
没有配 HTTPS（443 实测 closed），所以现在没有冲突。
