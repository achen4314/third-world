## 1. 结论先说

**修复前：28 项检查中 6 项不通过，其中 1 项是真实可利用的越权口子。**
**修复后：28/28 全部通过。**

| 阶段 | 通过 | 不通过 |
|---|---|---|
| 核查初版（2026-11-14 02:16） | 17 | **6** |
| 执行 0004 加固 + 前端角色映射后（02:22） | **28** | 0 |

最关键的一条：`anon` 角色在**全部 17 张业务表**上持有 `INSERT / UPDATE / DELETE / TRUNCATE` 权限。这是 Supabase 项目的默认权限（`pg_default_acl` = `arwdDxtm`）造成的，不是我们脚本写的。

为什么危险：**RLS 只拦 DML 的行级访问，`TRUNCATE` 完全不受 RLS 约束。** 只要存在任意一条"能把 SQL 以 anon 身份执行"的路径（注入、被误授的 RPC、错配的 key），就能一张表一张表清空，而 RLS 一点都不会报错。这类口子平时测不出来——因为正常业务路径根本不会去 TRUNCATE。

已用 `0004_rbac_hardening.sql` 修掉，并同时收掉 `TRUNCATE / REFERENCES / TRIGGER` 三个 DDL 级权限（`TRIGGER` 权限可以往表上挂触发器，等于能改数据流，RLS 同样管不到）。

## 2. 核查覆盖面（四层 28 项）

| 层 | 查什么 | 项数 |
|---|---|---|
| A 结构 | 主键、`org_id` 外键、`athlete_id` 级联、`updated_at` 触发器、外键索引、枚举、孤立表 | 7 |
| B 权限 | RLS 开关、策略覆盖、策略是否漏给 `public`、审计表只追加、`anon` 权限、`TRUNCATE`、默认权限、`SECURITY DEFINER` 的 `search_path`、函数执行权、角色分级、存储桶与策略、Realtime 发布前置条件 | 15 |
| C 动态 | 以 `anon` / 无归属 `authenticated` 身份**逐表实读 17 张表** | 2 |
| D 跨层 | 前端 7 个展示角色是否都能落到库内 `app_role` 枚举 | 2 |

设计上刻意做了两件事，避免"假通过"：

1. **C 层是实读，不是看策略存在与否。** 切到 `role anon` 并注入 `request.jwt.claims`，逐表 `select count(*)`，全程在事务内、结束 `rollback`，库内零残留。
2. **策略数量不做断言。** 数量对不代表语义对（比如把 `USING (true)` 写成一条也满足数量），所以只断言"非法状态为 0"。

## 3. 发现的问题与处理（6 项）

| # | 层 | 问题 | 严重度 | 处理 |
|---|---|---|---|---|
| 1 | B | `anon` 在 17 张表上持有 `INSERT/UPDATE/DELETE/TRUNCATE`（`TRUNCATE` 绕 RLS） | **高** | `revoke all on all tables/sequences in schema public from anon`；并用 `alter default privileges` 让**将来**新建的表也不再自动授给 anon |
| 2 | B | `authenticated` 也持有 `TRUNCATE/REFERENCES/TRIGGER`（应用侧永远用不到，纯扩大攻击面） | 中 | 逐项 `revoke` + 同步改默认权限 |
| 3 | B | 平台函数 `rls_auto_enable()` 是 `SECURITY DEFINER` 且 `anon` 可执行 | 低 | 收回 `public/anon/authenticated` 的 `EXECUTE`；事件触发器以属主身份运行，不受影响 |
| 4 | A | 9 个外键列无索引：`activities.org_id`、`test_sessions.org_id/created_by`、`daily_metrics.metric_id`、`athletes.team_id`、`athlete_grants.user_id/granted_by`、`memberships.team_id/granted_by` | 中 | 建 9 个索引。父行删除时不再逐行全表扫，也避免组织级看板走 seq scan |
| 5 | A | `device_credentials` / `daily_metrics` 有 `updated_at` 却无更新触发器，时间戳靠调用方自觉写 | 低 | 补 `touch_updated_at` 触发器，与其余 5 张表统一 |
| 6 | D | 前端角色 `head_coach / medical / admin` 在库内 `app_role` 枚举里**根本不存在** | **高** | 加显式 `ROLE_MAP`（`head_coach→team_admin`、`medical→clinician`、`admin→org_admin`），并在「角色与权限」页把映射直接显示出来 |

第 6 条为什么算高：前后端各有一套角色名，靠"约定"对齐，一旦有人在库里按 `head_coach` 写入 membership，外键/枚举会直接拒；更糟的是反过来——前端以为有权限、服务端按 `team_admin` 判，界面与实际放行不一致。这类问题不会报错，只会"某个按钮点了没反应"。

### 3.1 一个改不动的东西（如实记录）

`supabase_admin` 角色也持有一份默认权限，同样把 `arwdDxtm` 授给 `anon`。`postgres` 不是 `supabase_admin` 的成员，`alter default privileges for role supabase_admin ...` 实测报 **42501 permission denied**。

影响面：只有当**表由 `supabase_admin` 创建**时才会生效（例如在 Dashboard 表编辑器里点出来的表）。本项目所有迁移都由 `postgres` 执行，所以不受影响。核查脚本把它作为"可见化"项保留，期望值写死为平台现状，不让它变成永远红色的噪音；同时把这条限制写进了 0004 的注释，避免后人以为是漏改。

**推论（写进开发规范）：建表只能走迁移脚本，不要在 Dashboard 里手点建表。** 手点建出来的表没有 RLS、没有策略、anon 还带 TRUNCATE。

## 4. 表结构关系：核查后的实际形态

17 张业务表（不含分区子表 `raw_samples_default`），关系如下：

```
orgs ─┬─ memberships ──── app_users ──── auth.users（Supabase 托管）
      │        └─ teams ──┐
      │                   │
      ├─ athletes ─────────┴─ athlete_grants
      │     ├─ devices ────── device_credentials（无策略 = 仅 service_role）
      │     ├─ activities
      │     ├─ raw_samples（按 ts 分区，PK 含分区键）
      │     ├─ daily_metrics ──── metric_registry（30 条口径，唯一公式源）
      │     └─ test_sessions ─┬─ jump_tests（1:1，主键即外键）
      │                       └─ vbt_sets（1:N）
      ├─ consents（挂 app_users，不挂 athlete）
      └─ audit_logs（org_id 故意无外键）
```

核查确认的四条结构性事实：

1. **17/17 有主键**，没有无主键表。
2. **8 张表带 `org_id`，7 张带 `athlete_id`；所有 `athlete_id` 外键都是 `ON DELETE CASCADE`** —— 删运动员即连带清空其全部训练与健康数据，这是 PIPL 删除权能一次做完的前提。
3. **`raw_samples` 是分区父表（`relkind='p'`）**，主键 `(id, ts)` 含分区键，符合 PG 分区要求；索引建在父表上会下推到子表。
4. **`audit_logs.org_id` 是唯一一个"看着该建外键但故意不建"的列**：组织注销后审计仍须留存。已在库里写 `COMMENT ON COLUMN` 固化这个决定，核查脚本也把它列入白名单（白名单外的 `org_id` 缺外键仍然判失败）。

有一处**结构性不对称**值得记住（不是缺陷，是取舍）：

- `consents` 挂在 `app_users` 而不是 `athletes`。因为同意是"人"的行为，同一人可能在多个组织下都是运动员；挂在 athlete 上会导致重复同意记录、撤回时不知道该撤哪条。
- 代价：导出某个运动员的数据时，只有**他本人**调用才会带出 consents（RLS 只放行本人），教练导出时 `consents: []`。这是对的，但必须在导出接口的 `notes` 里写明，否则会被误判为"漏数据"。已在 `export-athlete-data` 的返回体里写明。

## 5. 权限层级：核查后的实际判定链

### 5.1 三层判定，逐层收窄

```
第 1 层  组织隔离     is_org_member(org_id)          —— 跨租户一律不可见
第 2 层  角色分级     is_org_member(org_id, roles[]) —— 7 个角色分「可写 / 只读」
第 3 层  对象级授权   can_read_athlete / can_write_athlete
                      └ 本人 ∪ 单人授权(athlete_grants) ∪ 同组织(且同队)
```

关键实现细节（都已核查）：

- 三个判定函数全部 `SECURITY DEFINER` + **`set search_path = public, pg_temp`**，避免策略自引用递归，同时杜绝 `search_path` 注入。
- 对 `public` 与 `anon` 执行 `revoke execute`，只授 `authenticated`——核查项「anon 可执行的 `SECURITY DEFINER` 函数 = 0」已通过。
- `device_credentials` **一条策略都没有**。这不是漏写：RLS 开启 + 零策略 = 默认拒绝，只有 `BYPASSRLS` 的 `service_role` 能碰。核查脚本把"无策略的表"期望值写死为 `device_credentials` 单张，任何其他表掉进这个状态都会失败。

### 5.2 角色读写分级（库内枚举 7 个）

| 库内角色 | 前端展示名 | 可写范围 | 只读范围 |
|---|---|---|---|
| `athlete` | 运动员 | 本人数据、本人设备 | 本人 |
| `coach` | 教练 | 本队运动员全量数据 | 本队 |
| `team_admin` | 主教练 | 本队运动员 + 队伍信息 | 组织成员与授权（不可改） |
| `clinician` | 队医 / 康复 | 本队运动员全量数据（含健康类） | 本队 |
| `analyst` | 科研 / 数据 | —（纯只读） | 本队（含原始样本下钻） |
| `org_admin` | 管理员 | 组织全量，含成员与角色 | 全组织 |
| `observer` | 只读观察者 | — | 组织聚合看板 |

**硬规则（三条，核查已验证）：**

1. 个人设备 / 训练 / 健康指标：能读到 → 可读；`can_write_athlete` 为真 → 可写。二者不是同一集合，`analyst` / `observer` 天然落不进可写集。
2. `device_credentials`：无策略 = 只有 `service_role`。
3. `audit_logs`：只追加。`revoke update, delete from authenticated, anon` —— 核查项通过。

### 5.3 存储层与数据库层的一致性

存储策略没有另立一套判断，而是直接复用上面三个函数：

| 桶 | 路径 | 读 | 写 |
|---|---|---|---|
| `activity-files` | `{org}/{athlete}/…` | `can_read_athlete(第2段)` | `can_write_athlete(第2段)` |
| `session-videos` | `{org}/{athlete}/…` | 同上 | 同上 |
| `exports` | `{org}/{user}/…` | 第2段 = `auth.uid()` | 第2段 = `auth.uid()` 且 `is_org_member(第1段)` |
| `avatars` | `{user}/…` | 本人 ∪ `shares_org_with` | 仅本人 |

路径段转 uuid 用 `arc_uuid_or_null()`：非法值返回 `null` → 策略判 `false`，**不抛 22P02**。若直接 `::uuid` 强转，攻击者只要用一个非 uuid 路径上传就能让接口吐 500 并泄露错误细节。

行为已实测（夹具写入真实 `storage.objects`，事务内按角色读，结束回滚）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 同组织教练读本队运动员文件 | 1 行 | 1 ✓ |
| 同组织教练读别的 athlete 目录 | 0 行 | 0 ✓ |
| 外组织用户读同两个对象 | 0 行 | 0 ✓ |
| `anon` 读 `activity-files` | 0 行 | 0 ✓ |

## 8. 一句话总结

结构关系没有断链（17/17 主键、级联完整、分区正确、无孤立表）；权限层级"组织 → 角色 → 对象"三层收窄，存储层复用同一套判定，没有第二套真相。
**唯一的真漏洞是 Supabase 默认权限把 `TRUNCATE` 之类的整表权限授给了 `anon`，而 `TRUNCATE` 不受 RLS 约束——已修。** 其余 5 项是索引、触发器与前后端角色命名不一致，均已修复并回归到 28/28。
